# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Tonnage**: an Android-first order and dispatch app for a group of steel companies (one owner, several companies each with its own GSTIN, plants under each company). Flow: order → sub-order per company → truck assignment → plant weighment (tare/gross, net = dispatched) → broker commission ledger.

Delivery is **frontend first**: the whole app (milestones F1–F5) runs on an in-app mock API, then the real backend (B1–B5) is built to the same contract. Done: F1 (app foundation: sign-in, app shell, admin screens, demo tools), F2 (masters and orders: customers/brokers/transporters, products, Home, Orders, order detail, the new-order wizard, the order lifecycle), F3 (dispatch and offline weighment: assign vehicle, Dispatch board, supervisor capture on a device store with outbox and sync, Needs attention) and F4 (money and reports: broker dues, ledger, record/reverse payment, the seven reports; Excel/PDF export and the broker statement PDF, plan Task 7, are on hold and their buttons show disabled "Coming soon") and F5 (notifications list and simulated push, background sync for supervisors, Graphite dark polish, accessibility pass; the client dropped Excel import, tablet split views and the demo APK from F5) and B1 (API foundation: `apps/api` on Fastify, Drizzle and Postgres with RLS, the M1 routes for auth, me, companies, plants, users and settings) and B2 (orders on Postgres: the M2 routes, contract suites M1 + M2 green against the API, permission matrix and money-leak checks).

## Commands

Run from the repo root (pnpm workspaces; Node 22; Windows, Git Bash or PowerShell).

```sh
corepack enable          # once; provides the pinned pnpm
pnpm install
pnpm lint                # eslint, every package
pnpm typecheck           # tsc --noEmit, every package
pnpm test                # vitest (packages, apps/api) + jest (apps/mobile)
pnpm dev:db              # embedded Postgres 16 for the API (port 54328); prints the .env URLs
pnpm db:migrate          # schema, role tonnage_app, RLS (needs apps/api/.env, from .env.example)
pnpm db:seed             # the sample world's org layer and masters, same ids as the mock; idempotent
pnpm dev:api             # Fastify on :3000
```

Single tests:

```sh
pnpm --filter @tonnage/shared exec vitest run src/units.test.ts
pnpm --filter @tonnage/contract-tests exec vitest run -t "LAST_OWNER"
pnpm --filter @tonnage/api exec vitest run test/org.test.ts
pnpm --filter mobile exec jest test/shell.test.tsx
pnpm --filter mobile exec jest -t "switching person"
```

Run the app (Expo Go, no native build):

```sh
cd apps/mobile
npx expo start             # scan the QR code with Expo Go on a phone on the same Wi-Fi
npx expo start --android   # or open it in a running Android emulator
```

Do not set `CI=1` while developing: Metro then disables reloads. If Metro answers 500 with `Unable to resolve` for a file that exists (new files on Windows), restart it with `--clear`. For the emulator, `npx expo start --localhost` plus `adb reverse tcp:8081 tcp:8081` and opening `exp://127.0.0.1:8081` survives Wi-Fi address changes. When driving the emulator with `adb shell input text`, focus a real `EditText` first: keys typed with nothing focused reach Expo's dev shortcuts (`r r` reloads, `i` opens the inspector).

## Architecture

```
apps/mobile (Expo Router)
  screens/hooks ─▶ src/api/client.ts ─▶ Transport ─┬─▶ packages/mock-api   (EXPO_PUBLIC_API_MODE=mock, default)
                                                   └─▶ HTTP to apps/api    (EXPO_PUBLIC_API_MODE=http, B milestones)
packages/shared ── zod schemas · policy · redaction · units/formatters · error codes   (used by mobile, mock and future API)
packages/contract-tests ── one HTTP-level suite run against any Transport
apps/api (Fastify + Drizzle on Postgres) ── the real backend, built to the same contract
```

- **One seam.** The app talks to a backend only through `Transport` (`packages/shared/src/transport.ts`). Screens and hooks never know whether the mock or the real API is behind it. Switching to the real API must be a config change, not a screen change.
- **The mock behaves like the real API.** `packages/mock-api` validates with the shared zod schemas, authorises with `policy.ts` + plant scope, redacts with `redactForRole`, returns the spec's error bodies `{ code, message, details? }`, honours `Idempotency-Key` and optimistic `version`, and simulates token expiry so refresh runs. Out-of-scope records are 404, never 403. Every route declares an `action` or `public: true`, or the router throws when it is built. The store persists to AsyncStorage.
- **`apps/api` (B1, B2):** Fastify + Drizzle on Postgres, the M1 routes (auth, me, companies, plants, users, settings) and the M2 routes (parties, products, orders, drafts, Home, the order lifecycle; vehicle requests wait for B3). Tests run on embedded Postgres 16. Tenant isolation is RLS with the non-owner role `tonnage_app` (migrations and the seed use the owner URL). The seed holds the sample world's org layer and `SAMPLE_MASTERS` with the mock's ids (no demo orders). The M1 and M2 contract suites run green against it (`M1_SUITES` + `M2_SUITES`, via `apps/api/test/contract.test.ts`), with a generated permission matrix (`policy-matrix.test.ts`) and a money-leak check over every GET (`money-leak.test.ts`). Each request transaction sets `lock_timeout` / `statement_timeout` (`DB_LOCK_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS`); deadlock, serialization failure and lock timeout answer 503 `BUSY` with `Retry-After`.
- **The contract suite is the definition of done** for both backends (`packages/contract-tests`). It runs against the mock now and must run green against the Fastify app in the B milestones. A change to behaviour starts with a contract test.
- `packages/shared` and `packages/mock-api` import nothing from React Native or Expo.
- **Numbers.** Quantities are integer kg; money is integer rupees; rates are whole ₹ per MT. No floats in stored values or in arithmetic on them. Unit basis (`mt` | `kg`, per user, `preferences.unitBasis`) only changes display and input: MT shows 3 decimals, kg whole numbers. Use the formatters in `packages/shared/src/units.ts` / `format.ts`; never format quantities by hand. Business time zone is `Asia/Kolkata`.
- **Roles:** `owner | city_staff | plant_head | supervisor`. A supervisor has exactly one plant, a plant head one or more, owner and city staff none (they see all). Money fields are omitted (not null) for plant head and supervisor. Tabs per role live in `apps/mobile/src/nav/tabs.ts`.
- **Business rules are pure functions** in `packages/shared/src/rules/` (pricing and rounding, quantities, derived status, numbering by IST financial year, edit limits). The mock and the API (B2) both use them, and the app uses them for previews; the server's numbers win. Status is derived, never stored.
- **Mock writes are all-or-nothing:** routes marked `transactional: true` (every order write) are rolled back if the handler throws, like a DB transaction in B2. Auth/OTP routes are not, because refusals must be recorded.
- **Trucks and dispatch (F3):** trucks are created by the assign action (the fixtures and the demo seed also add some). Dispatch is one transactional handler per sync event (AT_GATE, TARE, GROSS). TON-57: TARE needs the truck marked arrived first (`ARRIVAL_REQUIRED`); GROSS saves the weights and puts the truck in `weighed` ("Awaiting approval", still an open truck, nothing dispatched, the phone's task is done; a later TARE/GROSS is `ALREADY_WEIGHED`). The owner or city staff approve it (`POST /v1/trucks/:id/approve`, `dispatch.approve`), and the approval is the dispatch: `dispatchedAt` = approval time, a loading-slip number (IST financial year numbering), the broker earning, the tolerance close. Owner and city staff change weights while weighed and after dispatch (`weighment.correct`). Rulings 9–20 of the TON-57 plan. AT_GATE on a dispatched or cancelled truck is an accepted no-op (also on at_gate/loading). Tolerance close: when, after a dispatch, the sub-order's pending quantity is at most the tenant's completion tolerance (default 1,000 kg) and no other truck of that sub-order is open, the remaining lines close as `tolerance`; a correction that pushes pending back above it undoes the close. The supervisor marks the truck **Arrived** (`at_gate`, sync event `AT_GATE`; "At gate" is gone from the UI) before its tare can be captured (`useMarkArrived`); the owner weighing from truck detail records the arrival with the tare. Gross is never typed: the supervisor enters one weight per product line (`LineWeightsStep`, rule `checkLineWeights`: every line weighed, at least one above 0, tare + Σ ≤ 100 MT), may add another line of the same sub-order (`Task.lines`), and the app sends `grossKg = tare + Σ` with the lines above 0. Over or under the plan is information only (no plausibility question). Events the server refuses become rejections (`TRUCK_CANCELLED`, `TARE_CONFLICT`, ...) that surface in More → Needs attention, where the owner restores or dismisses them. After dispatch a weight correction rewrites the earning from the truck's original snapshot rates; before approval it only replaces the weights. Progress everywhere is five steps (`stepIndex`: Assigned, Arrived, Tare weighed, Weighed, Dispatched). Truck detail lists the plant's active supervisors (`Truck.supervisors`, not on the board) with Call and WhatsApp links built only for a normalised Indian mobile (`src/format/contactLinks.ts`).
- **Offline (`apps/mobile/src/offline/`):** a device store per signed-in user (`tonnage-device-<userId>.db`, SQLite via `sqliteDeviceStore.ts`; an in-memory store in jest/web), both held to `deviceStoreContract.ts`. Tables: tasks, done_today, outbox, sync_meta; no prices on the device. Outbox statuses: `pending | sending | accepted | rejected | blocked | resolved` (`blocked` = behind a rejected event for the same truck; `resolved` = the owner restored/dismissed the rejection, reported by `TasksPage.resolved`). `syncEngine.ts` pushes in `device_seq` order; `useSync` triggers on foreground, every 60 s, and after a save, with backoff 2 s x 2^n +/- 20 % up to 5 min. "Online" is the result of the last request, so Demo tools Offline works. Reset demo data clears every device store on the phone. After adding a native-backed package (expo-sqlite), restart Metro with `--clear`.
- **Demo trucks:** the seed has trucks at various states on the demo orders, so the Dispatch board and supervisor Tasks are populated after Reset demo data. Dispatched demo trucks have round plans and nets 2.8 % under to 1.4 % over, so Over / under loading has data. CG 04 LT 6619 (Borai) is weighed and awaiting approval, so To approve has one.
- **Order deletes and the phone (F4):** hard delete writes truck tombstones with `reason: 'deleted'`; `TasksPage.deleted` lists them and the phone marks those trucks' unsent outbox rows `resolved`. A cursorless pull returns `resolved`/`deleted` for the last 30 days only. Order edit, short-close, reopen, move-quantity and delete are idempotent and refuse a request without an `Idempotency-Key`. Restoring a rejection may return `warnings` (`VEHICLE_BUSY`, `OVER_ASSIGNABLE`), shown in the restore toast.
- **Broker money (F4):** the ledger is append-only, except that an order's hard delete removes its trucks' earning and reversal rows (payments stay, so the due can become an advance), and `amountRupees` is signed in the broker's favour: earning +, payment −(paid + TDS), a reversal is the exact negation of its row; `due = Σ amountRupees`, negative due shows as "Advance ₹X". Earnings are fixed at dispatch; a truck's first earning is dated by its `dispatchedAt` (IST). A weight correction's reversal and replacement earning both count on the correction date, so a later month moves only by the difference; "oldest paid first" (unpaid kg) still places the replacement on the truck's dispatch date (`LedgerRow.fifoDate`). Payments: whole rupees, TDS ≤ paid, UTR (4–30 letters/digits) required for NEFT/UPI, `paidOn` not in the future nor over 365 days back; only payments can be reversed, once, with a 3–200 character reason. Pure rules live in `packages/shared/src/rules/ledger.ts`. Routes: `GET /v1/brokers/dues`, `/v1/brokers/:id/ledger`, `/v1/brokers/:id/statement`, `POST /v1/brokers/:id/payments`, `POST /v1/ledger/:id/reverse` (owner and city staff; plant roles 403). The seed has one NEFT payment to R.K. Agarwal.
- **Request vehicle:** asks a customer or broker (Call / WhatsApp) to send a truck for an order's pending material; permission `truck.assign`. Entry points: order detail footer [Request vehicle][Assign vehicle] (Short close only in the ⋯ sheet) and the Dispatch board's two floating buttons (Request vehicle opens `/pick-loading?mode=request`, orders with pending > 0, then the sheet). `RequestVehicleSheet` (Send to / Material / Message): default recipient is the broker's first WhatsApp-capable number, else the customer's, else the first number of either (`defaultRecipient`); MT inputs are clamped to [0, pending] (a 0 line is unticked, total 0 disables both actions); the message is rebuilt from the choices until the person edits it (then a small "Update message" link); message quantities use the tenant's `externalUnitBasis`, not the viewer's unit basis; `{plant}` only when the company has exactly one active plant. Call opens `tel:`; WhatsApp opens `wa.me` and is enabled only for a WhatsApp-tagged number that `normalizeIndianMobile` accepts (else "call only"); Copy uses `expo-clipboard`; the record is sent after `canOpenURL` resolves true, just before `openURL` (no WhatsApp: toast, nothing recorded). Route `POST /v1/orders/:id/vehicle-requests` (`truck.assign`, idempotent, transactional, 201 `{ request }`): 422 `VALIDATION` for a line not on the order, closed or over pending (`lines.N.kg`), `totalKg` ≠ Σ kg, or `partyId` not the order's customer/broker; out of scope 404; writes activity `order.vehicle_requested`. `Order.vehicleRequests` holds only open requests: open until a truck that is not cancelled is assigned after (not at) the request time to any of its sub-orders, or its lines close / have nothing pending; a plant head sees a request trimmed to the lines (and their total) of their sub-orders (rules in `packages/shared/src/rules/vehicleRequest.ts`, handler `packages/mock-api/src/handlers/vehicle-requests.ts`). Order detail Trucks shows an amber note for the newest open request ("+N earlier" for older ones, "· waiting to send" while queued; tapping it reopens the sheet prefilled; for roles without `truck.assign` it is plain text, not a button). Offline: a network error or a 5xx saves the request with its Idempotency-Key in a per-person AsyncStorage queue `tonnage-vehicle-requests-<userId>` (`src/offline/vehicleRequestQueue.ts`), flushed on app foreground, 2 s after any successful request, and after a send (one flush per person at a time), and cleared by Reset demo data; the note shows at once from the optimistic cache. The seed has one open request on the R.K. Agarwal order. WhatsApp green is the token `wa` (#15803D).
- **Reports (F4):** `GET /v1/reports/:kind` for `dispatch-register | pending-orders | unit-sales | broker-wise | customer-wise | product-wise | loading-variance` (`reports.view`, owner and city staff). The mock builds flat facts (`packages/mock-api/src/report-facts.ts`) and calls the shared aggregators (`packages/shared/src/reports/`), so B4's SQL can be checked against the same functions. Ranges are inclusive IST dates, `to ≥ from`, at most 366 days, `to` not after today (422 otherwise); pending orders ignores the range. Every lifted ₹ is Σ per line `roundHalfUp(netKg × (rate + overprice), 1000)`, so every report's lifted ₹ and kg agree with the dispatch register. Broker-wise is ledger-based (rates fixed at dispatch, ledger dates), so its ₹ and kg follow the ledger, not the register. At most 5,000 rows plus `truncated`.
- **Notifications (F5):** shared `packages/shared/src/notifications/` holds the 10 kinds (TON-57 added `truck.weighed` for approvers and `truck.arrived`: plant head alerted, owner and city staff a `row`-only delivery that is never pushed) (strict payloads of kg/₹ integers and names), who is told (`recipientsFor`: never the actor, plant scope, money kinds to money roles only), the board 37 copy (`renderNotification`, rendered on the phone in the viewer's unit basis) and per-role deep links with an allowlist (`isAllowedDeepLink`; the phone never follows anything else). The mock writes rows and push-outbox entries inside the business transaction and drains the outbox to registered devices only after the request committed (`notifications.ts`, `pipeline.ts`); the aged-orders digest runs once per IST day from 09:00 on the first request; hard delete purges an order's notifications. Routes: `GET /v1/notifications` (30 a page, 30 days), `/unread-count`, `POST /:id/read`, `/read-all`, `POST|DELETE /push-token`. One token per phone: registering moves it to the new person, and a signed-out or revoked session drops its device.
- **Push (F5):** the only seam is `apps/mobile/src/notifications/pushChannel.ts` (mock: the in-process push worker; B4: Expo push). `usePush()` registers this phone for the signed-in person, shows alerts as phone notifications (expo-notifications local notifications work in Expo Go; remote push does not), turns silent `sync` pushes into `requestSync()`, and opens a tapped notification (also one that started the app). Permission is asked once per phone; Settings / Profile show "Phone notifications". Sign-out unregisters in the background via `onSignOut`. On one phone you are never told about your own actions: Demo tools → "Simulate someone else's action" makes another person act.
- **Background sync (F5):** `src/offline/backgroundSync.ts` registers `tonnage-sync` (15 min) for capture roles while signed in. Expo Go reports background tasks Restricted and never runs them, so registration is skipped there and Demo tools → "Run background sync now" runs the same body; real runs need a dev build. The foreground loop and the task share `withSyncLock` (one run at a time; a stuck run blocks at most 2 min).
- **Theme and accessibility (F5):** every colour is a token (a lint rule refuses colour literals outside `tokens.ts`); `test/dark-theme.test.tsx` fails on any colour outside the active palette and `test/contrast.test.ts` holds text pairs to WCAG AA (dark `inv` and `invtx2` were moved from the canvas values to pass). `test/a11y/audit.ts` checks a rendered screen like TalkBack (role, something to read, 44 dp touch box including hit slop, a header) and runs over every screen. Sheets fade instead of sliding with the phone's Remove animations on.
- **Welcome, tours and tips (canvas 41–46, `src/onboarding/`):** one layer mounted in `app/(app)/_layout.tsx` (`TourProvider`, in the tree, not a Modal, so the lock screen covers it) shows one thing at a time: Welcome back (`WelcomeScreen`, when the session resumed from storage or after unlock; on screen 1.5 s then fades, never dismissed by a tap; a tapped notification closes it via `dismissWelcome`), the first sign-in intro (`TourIntroSheet`), a spotlight tour (`stepsFor(role)`, copy in `tours.ts`; targets are `TourTarget` wrappers on real screens that report `measureInWindow` rects to `targetsStore`), or a first-visit tip (`useFirstTip(key)` on nine screens, `tips.ts`). Tours and tips wait while a `Sheet` is open (`onboardingStore.openSheets`) or the app is locked. Progress (`introSeen`, `tourDone`, `tipsOn`, `tipsSeen`) is per person on the phone in AsyncStorage `tonnage.onboarding`; Reset demo data clears it, Demo tools → Replay first sign-in replays it for the current person. Help & tour is `/help` (More, or Profile for supervisors): replay, the other roles' tours as card previews (owner and city staff), "How do I…" (`howTo.ts`), tips on/off. Tour copy must not mention "Gross weighed" or "save to dispatch" (a test refuses it).
- **Expo Go only.** No custom native modules; anything that needs a dev client is out until the plan says otherwise. Expo SDK modules that ship in Expo Go are fine (expo-notifications, expo-background-task, expo-task-manager); restart Metro with `--clear` after adding one.

### Mobile layout (`apps/mobile`)

- `app/`: Expo Router routes. `(auth)` = sign-in, verify, demo sign-in; `(app)` = signed-in area with `(tabs)` plus companies, users, settings, demo-tools.
- `src/api/`: `client.ts` (auth headers, refresh, idempotency, retry), `transport.ts` (mock vs http), `hooks/` (TanStack Query hooks), `demo.ts` (demo-tools gating).
- `src/auth/`: session (SecureStore tokens) and fingerprint lock (after 15 min idle).
- `src/ui/`: primitives built on `src/theme/tokens.ts`. Colours, copy and spacing come from the design canvas; use tokens, never raw hex (lint enforces it). Text inputs take `inputTheme(t, scheme)`.
- `src/notifications/` (push channel, `usePush`, local notifications, permission, safe links) and `src/screens/notifications/` (list, row, Home bell, permission row); `src/a11y/` (`useReduceMotion`).
- `src/screens/`: screen components; route files in `app/` stay thin. `src/screens/orders/` also holds the request-vehicle sheet and note (`RequestVehicleSheet`, `requestVehicleParts`, `requestVehicleState`, `vehicleRequestNote`), with hooks in `src/api/hooks/vehicleRequests.ts` and the offline queue in `src/offline/vehicleRequestQueue.ts`.
- `src/screens/supervisor/` (Tasks with Vehicle arrived, capture, `LineWeightsStep`, Dispatched / Weights saved, Done today, sync banner), `dispatch/` (board with To approve, assign vehicle, truck detail, `ApproveSheet`, `SupervisorCard`, cancel, correct / change weights), `attention/` (Needs attention), `money/` (Broker ledger dues list at `/brokers`, broker profile and ledger shown on a broker's party page, Record payment, reverse), `reports/` (Reports at `/reports`: tiles, range sheet, preview, Share). `src/ui/CalendarSheet.tsx` is the pure-JS IST date picker (no native picker).
- `src/screens/create/`: the New tab is not a destination. Its press is caught in the custom tab bar's `onPress` in `app/(app)/(tabs)/_layout.tsx` (this bar emits no `tabPress`) and opens `CreateSheet` (canvas 39) over the current tab. The tiles are in `createOptions.ts`, each gated by a policy action: Order `order.create`, Loading `truck.assign`, Customer/Broker/Transporter/Product `masters.manage`. Loading opens `/pick-loading` (`LoadingPickerScreen`): open and partly dispatched sub-orders from the existing orders list plus each order's detail (no route of its own), following the unit switcher and search, then `/assign/[subOrderId]`.
- `src/screens/new-order/`: the wizard. `wizard.ts` holds its pure state (draft ↔ request body ↔ order, preview totals); `useDraftAutosave` keeps server-side drafts. `/order-form` = fresh order (the Create sheet's Order tile and the Orders first-run button); `?orderId|draftId|partyId` = edit, resume, start for a party. The `(tabs)/new` route still renders the wizard for deep links only.
- `src/prefs/unitFilter.ts`: the unit switcher's choice, per person on this phone; order and Home query keys include it.
- `src/nav/`: role tabs (`tabs.ts`), route guards, and `freshStart.ts` (a person switch resets the signed-in stack so no tabs or history carry over; this expo-router only accepts a complete state on RESET).
- `test/`: jest + React Native Testing Library; `test/router.test.tsx` runs the real tabs layout under `expo-router/testing-library`. In RNTL 14 `unmount()` and `fireEvent.*` are async: always `await` them (an un-awaited `changeText` races the next press), and use `advanceTimersByTimeAsync` with fake timers. Jest fake timers block debounced search; pin time with `jest.spyOn(Date, 'now')` instead. Seeded demo orders: `createMockApi({ seedOrders: true })` (the app does this; contract tests do not), and with them demo notifications. Give a test's `QueryClient` `mutations: { gcTime: Infinity }` when it runs mutations directly, or jest waits 5 min for the cache timer. `test/setup-after-env.ts` resets process-wide state (the sync lock) before every test.

## Demo tools

More → Demo tools. Shown only in mock mode in dev builds, or when a client demo build sets `EXPO_PUBLIC_DEMO_TOOLS=1`; never against the real API. They let you reset demo data, replay the first sign-in (welcome, intro, tour, tips), switch person, simulate Offline, set server latency (0 / 800 ms / 6 s "waking server"), and arm a failure for the next request (network error or an error code such as `STALE`, which only fires on writes). Switching person always turns simulated Offline off.

## Conventions

- Delivery: work on a branch, merge through a pull request with green CI (`verify`), update CHANGELOG.md, and tag each milestone on its merge commit.
- Commits: Conventional Commits with scope, e.g. `feat(mobile): …`, `fix(mock-api): …`.
- Tests first: a failing test before the fix or feature. CI (`.github/workflows`) runs lint, typecheck and test.
- Scripts must work in both Git Bash and PowerShell: no `rm -rf`, no `export X=`.
- When a business rule is unclear, check the decisions doc's Decided / Default / Open status before asking; build the Default and keep likely-to-change rules isolated and configurable.
